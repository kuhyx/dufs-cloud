Phase 4 — Multi-select: bulk move, zip-share & delete

A walkthrough of commit 4977776 in the dufs-cloud Flutter app: how long-pressing a file tile turns the browser into a multi-select tool, and the small design decisions that keep it correct and 100 % covered.

1 · Background

BrowserScreen is the app's home: it lists one cloud folder as a grid of tiles (EntryTile), each showing a thumbnail or type icon, a name, and a size. Tapping a folder navigates into it; tapping a file opens or downloads it. An overflow menu on each file tile already offered single-item Download and Delete.

The screen also carries the search/filter system added in Phase 3: an AppBar search box and a "Filters" sheet drive a lazily-built whole-cloud index (_index), and when a filter is active the grid switches from "the current folder" to "matches across the whole cloud, grouped by their folder". That index is a cache — it's rebuilt on first filter use and thrown away (_index = null) whenever something changes on the server.

Before this change there was no way to act on more than one item at a time. Moving five photos to an album meant five trips through a menu. EntryTile already had dormant selected / onToggleSelect parameters (a checkbox that showed only when selected != null), but nothing in BrowserScreen ever passed them. Phase 4 wires that up.

2 · Intuition

The whole feature rests on two pieces of state added to the screen:

bool _selecting = false;          // are we in selection mode?
final Set<String> _selected = {};  // which entry paths are ticked

A long-press on any tile flips _selecting to true and drops that tile's path into the set. While selecting, the normal AppBar (search box, filter, settings) is swapped for a contextual AppBar: a close button, a live count, and three actions. Tapping tiles now toggles their membership in the set instead of opening them.

Two correctness details are worth their own sentences:

  • A partial failure is not fatal. The batch helper _batch runs the op on every selected entry inside a try/catch, counting failures rather than throwing. Five deletes where one 500s ⇒ four gone, one reported in a snackbar — not an all-or-nothing abort.
  • Selection is scoped to the plain browse grid, not the filtered group view. Bulk zip and move assume every selected item shares one parent folder (the current _path) — the zip's archive paths and the move's destination are computed relative to it. Cross-folder filter results would break that assumption, so only the unfiltered grid is selectable.

3 · Code

a. Entering & tracking selection

A long-press seam is added to EntryTile (it just forwards to the body InkWell's onLongPress), and the screen gains the enter/toggle/exit helpers. Note that a tap while selecting toggles rather than opens:

void _enterSelect(DirEntry e) => setState(() { _selecting = true; _selected..clear()..add(e.path); });
void _toggleSelect(DirEntry e) => setState(() { if (!_selected.remove(e.path)) _selected.add(e.path); });
void _exitSelect()   => setState(() { _selecting = false; _selected.clear(); });

// in _grid(), only when selectable:
onTap: () => selectable && _selecting ? _toggleSelect(e) : unawaited(_open(e)),
onLongPress: selectable ? () => _enterSelect(e) : null,
selected: selectable && _selecting ? _selected.contains(e.path) : null,

b. The failure-tolerant batch runner

Move and delete share one helper. It returns how many items failed so the caller can surface a count instead of a stack trace:

Future<int> _batch(Future<void> Function(DirEntry) op) async {
  var failed = 0;
  for (final e in _selectedEntries) {
    try { await op(e); } on Exception { failed++; }
  }
  return failed;
}

c. Move — with a no-op guard

Move pushes the existing FolderPicker, then MOVEs each item. If the user picks the folder the items already live in (dest == _path) — or cancels — nothing is sent:

final dest = await Navigator.of(context).push<String>(… FolderPicker(initialPath: _path, count: …) …);
if (dest == null || dest == _path) return;  // cancelled, or a pointless self-move
final failed = await _batch((e) => client.move(e.path, dest));
_index = null; _exitSelect(); await _load(_path);

d. Download-as-zip — and the coverage trick

The zip path builds a STORE archive of the selection, writes it to a temp file, and hands it to the platform share sheet. The share call is injectable so tests never touch the share_plus platform channel — and the default is placed on the right of a ?? so an injected stub keeps it from ever being evaluated (identical trick to the pre-existing documentsDir / pickMedia seams). That is what lets the line count as covered without running native code:

final bytes = await buildSelectionZip(client, _path, _selectedEntries);
final file  = File(p.join((await getDir()).path, 'dufs-selection.zip'));
await file.writeAsBytes(bytes);
final share = widget.shareSheet ?? SharePlus.instance.share;  // RHS never runs in tests
await share(ShareParams(files: [XFile(file.path)]));

e. The contextual AppBar

build() now chooses between two AppBars, and hides the upload FAB while selecting:

appBar: _selecting ? _selectAppBar() : _browseAppBar(),
floatingActionButton: _client == null || _selecting ? null : FloatingActionButton(…),
Every mutating action — move, delete, zip's siblings upload/mkcol — sets _index = null. Because the Phase 3 filter reads from that cached whole-cloud index, forgetting to invalidate it would show stale search results after a bulk move. This is the seam where the two phases meet.
