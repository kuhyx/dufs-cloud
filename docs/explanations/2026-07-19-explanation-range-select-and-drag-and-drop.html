Background — what this code is

dufs-cloud is a personal file cloud. A dufs server exposes a directory over WebDAV, and two clients browse it: a React single-page app in web/, and a Flutter app in app/. Both show the same thing — a grid of tiles, one per file or folder — and both talk to the server through a small client wrapper with methods like list, upload, remove, and move(fromPath, destDir).

Both apps already had multi-select before this change. On the web you tick a checkbox on a tile; on mobile you long-press a tile to enter a selection mode, after which taps toggle items instead of opening them. Once things are selected, a toolbar offers move, download-as-zip, and delete. Selection lives in one place per app: a set of paths — selected in the React Gallery component, _selected in the Flutter _BrowserScreenState.

Two details from that existing design matter later:

  • The listing can change underneath the selection. Both apps reload the current folder after an operation, and the mobile app keeps a pull-to-refresh gesture live while you are selecting. Reloading replaces the entries list but does not clear the selection.
  • The mobile app renders two different grids. The normal folder grid is selectable; the grouped results shown while a search filter is active are not.

There is also a PDF viewer on mobile, PdfScreen. It writes the PDF into a temp directory, binds a loopback HttpServer to serve a bundled pdf.js viewer, and points a WebView at it. It appears here only because its test turned out to be broken, and that is what was keeping CI red.

Intuition — what changed and why

1. Selecting a range instead of one tile at a time

Selecting twelve consecutive files meant twelve clicks. The fix is the convention every file manager uses: click one item, then shift-click another, and everything between them — in the order currently on screen — becomes selected. The first item is the anchor.

A phone has no shift key. Rather than overload long-press — already spoken for, since it is what enters selection mode — the mobile app grows an explicit two-step gesture: a "Select range" button in the action bar arms the mode, the next tap extends from the anchor, and the mode disarms itself. The button tints with the theme accent while armed, so the state is visible rather than remembered.

2. The anchor can go missing

An anchor is just a path, remembered across renders. But the listing it points into can be replaced. On mobile, pull-to-refresh works during selection and does not clear it, so this is reachable: select a file, someone deletes it server-side, you refresh, and now the anchor names a file that is no longer in the list.

The range code looks the anchor up by index. A missing anchor yields index -1, and slicing a list from -1 throws. So both apps check, and fall back to treating the interaction as a plain toggle. This guard is genuinely reachable — an earlier reading of the code concluded it was dead and nearly deleted it. The test that proves otherwise drives a refresh whose second listing omits the anchor's file.

3. Dragging things around

On the web, tiles became draggable and folder tiles became drop targets, which buys two gestures at once: drag entries onto a folder to move them, and drag files in from the operating system to upload. Dropping on empty grid space uploads into the folder you are looking at; dropping onto a folder tile uploads into that folder instead. Dragging an item that is part of a selection carries the whole selection; dragging an unselected item carries just it.

Mobile gets the move half only — there is no OS drag source — and only inside selection mode, where long-press is free to mean "start dragging".

4. Two drops that must not happen

A folder dropped into itself, or into its own descendant, has no sensible answer: the subtree would have to become its own parent. And an item dropped into the folder it already lives in is a no-op worth skipping rather than issuing a pointless request for.

On mobile the same predicate also gates the drop target itself, so an illegal drag never even lights the folder up — the refusal is visible before you let go, not after.

5. The bug the tests missed

This is the part worth remembering. To read the shift key, the first implementation cancelled the checkbox's click and did the toggle by hand:

onChange={() => {}}
onClick={(e) => { e.preventDefault(); onToggleSelect(entry, e.shiftKey); }}

That works right up until you look at the box you clicked. React keeps a value tracker per controlled input so it can tell real changes from echoes of its own render. The browser toggles the checkbox before any handler runs, the tracker records the new value, and only then does preventDefault() put the DOM back. On the next render React compares its prop against the tracker, sees agreement, and writes nothing.

Every other checkbox updated correctly, because their props changed without a click and React wrote them normally. Only the clicked one went stale — and unticking it stuck for the same reason. The suite was at 100% coverage and did not notice, because the assertions checked the selection count and the neighbours' rendered state, never the clicked box's own.

The fix is to stop fighting the browser. For checkboxes React routes the change event through the click, so the modifier keys are already on the native event. Do the toggle in a plain onChange, read e.nativeEvent.shiftKey, cancel nothing — and the controlled-input contract holds.

6. A test that asserted nothing

The same shape of bug — a test that passes whether or not the code under test runs — was already sitting in pdf_screen_test.dart, and it was why CI was red at 1328/1329 lines.

The test meant to cover this window in PdfScreen._init(): between binding the loopback server and storing it in _server, the widget can be disposed. Because dispose() closes _server and _server is still null at that moment, nothing would ever close that server — one leaked loopback server, and its file-serving loop, per aborted PDF open.

The test never got near it. _init() was still unpacking the pdf.js viewer, blocked in an asset-bundle load that only resolves while the test binding is pumped — and the test only slept. So the gated download never resumed, the bind never happened, and the lone assertion ("no WebView is showing") was true either way. Seeding the extraction marker lets _init() skip straight to the download; the test now also asserts the PDF file was written, which is the step immediately before the bind, so it fails loudly if the flow ever stalls early again.

Two traps worth knowing, both hit while fixing this. Real I/O futures never complete in flutter_test's fake-async zone, so an await Directory(...).create() outside runAsync hangs the test outright — use the …Sync variants. And a future gated inside runAsync only resumes once control leaves it, so the waiting has to happen in a second runAsync.

Code — the walkthrough

The shared rule, written twice

Both apps needed the same drop predicate, and both already had a underPath helper. The rule reads directly: keep a path if the destination is not inside it, and if it does not already live there.

// web/src/lib/paths.ts
export function movableInto(paths, destDir) {
  return paths.filter(
    (p) => !underPath(destDir, p) && parentPath(p) !== normalize(destDir),
  );
}

underPath(destDir, p) covers both the self-drop and the descendant case in one test, since a path is considered under itself. The Dart version in app/lib/util/paths.dart is the same expression. Normalising the destination is what makes a trailing slash harmless.

Range selection

Each app keeps one extra piece of state — the anchor — updated on every plain interaction, and consults it when the range gesture fires. The web version:

function toggleSelect(entry, shiftKey) {
  if (shiftKey && selectAnchor !== null) {
    const anchorIdx = displayed.findIndex((e) => e.path === selectAnchor);
    const targetIdx = displayed.findIndex((e) => e.path === entry.path);
    if (anchorIdx !== -1 && targetIdx !== -1) {
      const [lo, hi] = anchorIdx < targetIdx ? [anchorIdx, targetIdx] : [targetIdx, anchorIdx];
      setSelected((cur) => new Set([...cur, ...displayed.slice(lo, hi + 1).map((e) => e.path)]));
      setSelectAnchor(entry.path);
      return;
    }
  }
  /* plain toggle, then: */ setSelectAnchor(entry.path);
}

Three decisions are encoded here. The range is taken over displayed — what is on screen right now — so it follows the current sort and filter rather than some server-side order. A range adds to the selection instead of replacing it, so ranges compose. And the anchor moves to wherever you just interacted, so a second shift-click extends from there.

Mobile mirrors it in _toggleSelect, with _rangeArmed standing in for the shift key and cleared after use. The fallback carries the comment explaining why it is not dead code:

// A pull-to-refresh during select mode can drop the anchor from the
// listing without clearing the selection; fall back to a plain
// toggle rather than extending from an index we no longer have.
if (anchorIdx != -1 && targetIdx != -1) { … }

The checkbox, restored to a normal controlled input

onChange={(e) => {
  const native = e.nativeEvent as Partial<MouseEvent>;
  onToggleSelect(entry, native.shiftKey === true);
}}

No onClick, no preventDefault, no empty onChange. The regression test pins the actual defect rather than its surroundings — it asserts the box you clicked reports checked === true, and that unticking it clears. It fails against the old handler, which is the only reason to trust it.

Web drag and drop

The grid owns the DOM plumbing. Drag payloads travel under a private MIME type, which is what keeps our own drags distinguishable from files arriving from the OS:

const DRAG_TYPE = "application/x-dufs-paths";

onDragStart={(e) => {
  const paths = isSel ? [...selected] : [entry.path];
  e.dataTransfer.setData(DRAG_TYPE, JSON.stringify(paths));
  e.dataTransfer.effectAllowed = "move";
}}

A folder tile's onDrop branches on dataTransfer.files.length: files present means an upload into that folder, otherwise decode the payload and move. It calls stopPropagation() so the drop does not also reach the grid background, which would upload into the current folder as well. The background handler on <main> ignores anything that is not an OS file drag, so internal drags never trigger a stray upload. Its onDragLeave checks currentTarget.contains(relatedTarget), because crossing a child tile fires a leave event that would otherwise flicker the highlight off.

The grouped search-results grid simply omits the drop handlers, which switches the whole feature off there — results span folders, so "the folder you dropped into" would be ambiguous.

Mobile drag and drop

In selection mode each tile is wrapped in a LongPressDraggable, and folder tiles additionally in a DragTarget. The gating is one line, and it is the whole reason the two gestures never collide:

onLongPress: selectable && !_selecting ? () => _enterSelect(entry) : null,
…
if (!selectable || !_selecting) return tile;
return _draggableTile(entry, tile);

Outside selection mode long-press enters selection; inside it, the draggable claims the press. onWillAcceptWithDetails runs movableInto so an illegal target never highlights, and _moveDropped filters again before issuing any request — mixed drags can be partly legal, so the predicate has to run on each item, not just on the batch.
