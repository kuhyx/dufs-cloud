# Design audit — dufs-cloud

Generated against safe-design-rules (anthonyhobday.com/sideprojects/saferules).
Report only — nothing in this repo was changed by the audit itself.

This repo has two UI surfaces, audited separately below: the Flutter mobile
app (`app/`) and the web app (`web/`).

---

## Flutter app (`app/`)

**Design-token entry point:** `app/lib/main.dart:21-31` — `MaterialApp` with
`theme: ThemeData(colorSchemeSeed: Colors.indigo)` and a matching
`darkTheme:` variant. There is no custom `ColorScheme`, no `theme.dart`, no
hand-picked hex values anywhere in the app — the entire palette, tonal steps,
and (via `Theme.of(context).textTheme`) most typography are generated by
Flutter Material 3's seed algorithm. Practical effect: rules that are about
*palette construction* (near-black/white, saturated neutrals, distinct
brightness steps, warm/cool consistency, closer-is-lighter, container
brightness limits) are delegated to Flutter's M3 algorithm rather than
authored in this repo, so they're marked N/A below rather than
Pass/Violation — there's nothing in-repo to point at. The real, actionable
findings are concentrated in the handful of places that bypass the theme.

### Violations

- **Rule 1 (near-black/near-white, not pure)** — `app/lib/screens/image_screen.dart:26,28,29,42` and `app/lib/screens/video_screen.dart:90,92,93,100` hardcode `Colors.black` / `Colors.white` / `Colors.white70` / `Colors.white54` for the viewer chrome instead of reading `Theme.of(context).colorScheme.surface`/`onSurface`. This bypasses the app's own near-black/near-white M3 tones with literal pure black/white, and does it in two different screens (duplicated, not centralized).
- **Rule 4 (everything deliberate)** — same two files: `settings_screen.dart` and `browser_screen.dart` consistently pull colors from `Theme.of(context).colorScheme.*` (e.g. `browser_screen.dart:676,846,858`), but `image_screen.dart` and `video_screen.dart` never reference the theme at all — an inconsistent, undocumented split between "themed" and "hardcoded" screens with no comment explaining why the viewers opt out.
- **Rule 11 (mathematically related measurements)** — spacing values across the app mix a 4px-ish scale (4, 8, 12, 16, 24) with one 6px value that fits neither a 4 nor 8 base: `app/lib/widgets/entry_tile.dart:66` `EdgeInsets.fromLTRB(6, 4, 6, 0)` and `:75` `EdgeInsets.fromLTRB(6, 0, 6, 6)`. Round to 4/8 (e.g. 4 or 8, not 6) to stay on the same scale as the rest of the app (`browser_screen.dart:708,784`, `settings_screen.dart:63`, `filter_sheet.dart:80`, `text_editor_screen.dart:105,111` all use 4-multiples).
- **Rule 20 (body text ≥16px)** — `app/lib/widgets/entry_tile.dart:71` renders the file name (the primary readable content in the grid tile) with `Theme.of(context).textTheme.bodySmall`, which is 12sp in Flutter's default M3 type scale. `:78` uses `labelSmall` (11sp) for the file size. Both are well under the 16px minimum for content users actually read.
- **Rule 26 (no shadows in dark interfaces)** — `app/lib/screens/browser_screen.dart:856-866` (`_dragFeedback`) sets `elevation: 6` on a `Material` widget with no dark-mode override. Since `main.dart:25-28` ships a real `darkTheme`, this Material shadow will render unchanged in dark mode — it's the one shadow in the app and it isn't suppressed for dark.
- **Rule 22 (button padding: horizontal ≈ 2× vertical)** — `app/lib/screens/browser_screen.dart:862` `EdgeInsets.symmetric(horizontal: 12, vertical: 8)` on the drag-feedback chip is a 1.5× ratio, not ~2×.

### Pass

- Rule 3 (high contrast for important elements) — `FloatingActionButton`, `FilledButton` etc. use unmodified M3 defaults, which already implement this.
- Rule 6 (letter-spacing/line-height by size) — delegated to M3's built-in per-level type scale (`textTheme.bodySmall`/`labelSmall`/etc. each carry their own height); no custom `TextStyle` overrides this except `video_screen.dart:100`, which only sets `color`.
- Rule 7 (border contrast) — `browser_screen.dart:846` uses `colorScheme.primary` for the drop-target border, which M3 guarantees is distinct from surrounding surfaces.
- Rule 17 (simple-on-complex) — no hand-built overlapping content compositions beyond standard M3 widgets.
- Rule 19 (outer padding ≥ inner padding) — `browser_screen.dart:784-789` grid padding (8) vs. tile spacing (8) and `filter_sheet.dart:80` sheet padding (12-24) vs. row gaps (12) both satisfy the "≥" bound (ties are fine).
- Rule 21 (line length ~70 chars) — mobile viewport widths (~360-400dp) naturally bound line length; no evidence of a violation.
- Rule 23 (two typefaces max) — the app uses exactly one Material type scale throughout; no custom `fontFamily` anywhere.
- Rule 27 (don't mix depth techniques) — only one shadow exists in the whole app (`browser_screen.dart:860`), so there's nothing to mix it with.
- Rule 28 (lower icon contrast paired with text) — `IconButton`/`Icon` usages throughout rely on default M3 `IconTheme`, which already applies this.

### Not applicable

- Rule 2 (saturate neutrals) — no hand-authored neutrals; delegated to `colorSchemeSeed: Colors.indigo` (M3 algorithm), nothing in-repo to grade.
- Rule 5 (optical alignment) / Rule 8 (align with something else) / Rule 12 (order by visual weight) / Rule 14 (space between high-contrast points) — require visual rendering to judge; no static finding either way.
- Rule 9, 10, 15, 18 (distinct brightness steps / warm-or-cool / closer-is-lighter / container brightness limits) — all delegated to the M3 seed algorithm; no hand-authored palette to check (except the Rule 1 violation above, which already bypasses this system).
- Rule 13 (12-column grid) — mobile single-column/grid-tile layout, not a web-style form grid.
- Rule 16 (shadow blur ≈ 2× offset) — the app's one shadow (`browser_screen.dart:860`, `elevation: 6`) is a Flutter Material elevation level; blur/offset are computed by the framework from the elevation value, not hand-authored, so there's no ratio in-repo to check.
- Rule 24 (nest corners) — `browser_screen.dart:849` (radius 12) and `:859` (radius 8) are sibling widgets, not nested, so the nesting formula doesn't apply.
- Rule 25 (avoid adjacent hard divides) — no hand-authored dividers/borders stacked back-to-back; relies on default `AppBar` elevation.

### Notes

- The app has no dedicated `theme.dart` — everything hangs off one `colorSchemeSeed` line in `main.dart`. That's a reasonable minimal approach, but it means the two viewer screens that opt out of it (`image_screen.dart`, `video_screen.dart`) are the *only* place hand-authored color/typography choices exist in the app, and both duplicate the same `Colors.black`/`Colors.white` pattern independently — fixing Rule 1 in one file won't fix the other.

## Web app (`web/`)

> `:root` block itself has since been *deleted*: the web app now consumes
> `@kuhyx/web-ui/tokens.css`, so palette, spacing, radius, type and shadows all
> arrive from the shared package (`~/utils/web_ui`). Verified against the
> current file: **0** occurrences of `#fff`/`#ffffff`/`rgba(0,0,0,…)`, 37
> `var(--space-*)` uses and 13 `var(--radius-*)` uses, i.e. the Rule 1, Rule 4
> and Rule 11 findings below are all closed. `:focus-visible` is styled by the
> shared layer and verified in a real browser at 1366x768 and 1024x600.
>
> Kept for the record rather than deleted, since the Flutter section above is
> still live.

**Design-token entry point:** `web/src/index.css:1-23` — `:root` CSS custom
properties (`--bg`, `--fg`, `--muted`, `--card`, `--border`, `--accent`,
`--danger`, `--overlay`) with a `@media (prefers-color-scheme: dark)`
override block. Nearly all component CSS below it consumes these variables
rather than hardcoding colors, so the palette itself is centralized. Spacing,
radius, shadow, and typography, however, are **not** tokenized at all — every
rule value is a literal `rem`/`px` chosen per-selector, so rules 6, 11, 16,
20, and 22 have to be checked value-by-value rather than against one source
of truth.

### Violations

- **Rule 1 (near-black/near-white, not pure)** — `web/src/index.css:2` `--bg: #ffffff;` is pure white in light mode (dark mode's `--bg: #0d1117` at line 14 correctly is near-black). Also several component rules hardcode pure `#fff`/`rgba(0,0,0,…)` instead of theme variables even where a themed token would work, e.g. `:95` `button.primary { color: #fff; }`, `:526` `.tile-act { color: #fff; }`, `:639` `.viewer-fallback { color: #fff; }`, `:651` `.viewer-close, .viewer-nav { color: #fff; }`.
- **Rule 2 (saturate your neutrals)** — same root cause as Rule 1: `--bg: #ffffff` (line 2) is a fully desaturated pure white, breaking the otherwise-consistent blue-tinted neutral family (`--fg`, `--muted`, `--card`, `--border` all carry a slight cool/blue tint in both light and dark, e.g. `--card: #f4f6f8` line 5, `--border: #d8dee4` line 6).
- **Rule 6 (adjust letter-spacing/line-height by text size)** — `web/src/index.css` declares `line-height` exactly once, at `:532` (`.tile-act { line-height: 1; }`, used only to vertically-center an icon glyph, not for text-size scaling) and `letter-spacing` **zero** times, despite font sizes ranging from `0.72rem` (`.group-count`, `:332`) up to `2.4rem` (`.tile-icon`, `:484`). No line-height/letter-spacing scale exists anywhere in the file.
- **Rule 11 (mathematically related measurements)** — spacing values are ad hoc rem literals with no shared scale: e.g. `:61` `padding: 0.6rem 1rem` (9.6px/16px), `:140` `padding: 0.35rem 0.5rem` (5.6px/8px), `:262` `padding: 0.1rem 0.3rem 0.4rem` (1.6/4.8/6.4px), `:409` `padding: 0.1rem 0.4rem` (1.6px/6.4px). None of these round to a common 4px or 8px base; there are 20+ distinct spacing values in the file with no evident scale.
- **Rule 15 (closer elements should be lighter)** — `.tile` (`:453-459`) uses `background: var(--card)` to sit "elevated" on the page background. In dark mode `--card` (`:17`, `#161b22`) is lighter than `--bg` (`:14`, `#0d1117`) — correct. In light mode `--card` (`:5`, `#f4f6f8`) is *darker* than `--bg` (`:2`, `#ffffff`) — the elevated surface goes the wrong direction in light mode.
- **Rule 16 (shadow blur ≈ 2× the offset)** — `web/src/index.css:259` `box-shadow: 0 8px 24px rgba(0, 0, 0, 0.35);` on `.extpicker-menu`: offset 8px should pair with ~16px blur; actual blur is 24px, 50% over.
- **Rule 20 (body text ≥16px)** — `web/src/index.css:501` `.tile-name { font-size: 0.82rem; }` (13.1px) sets the file name — the primary readable content in every grid tile — below the 16px minimum. Body text elsewhere correctly inherits the 16px default (`body` at `:33-39` sets no `font-size`, i.e. stays at 16px).
- **Rule 22 (button padding: horizontal ≈ 2× vertical)** — `web/src/index.css:140` (`.filterbar input, .filterbar select`) and `:234` (`.extpicker-btn`) both use `padding: 0.35rem 0.5rem` — a 1.43× ratio, not ~2×. Contrast with `.button.primary` (`:98`, `0.4rem 0.9rem` = 2.25×) and `button.ghost` (`:111`, `0.4rem 0.8rem` = exactly 2×), which do follow the rule.
- **Rule 26 (no shadows in dark interfaces)** — `web/src/index.css:259` (`.extpicker-menu` box-shadow) and `:209` (`.slider-thumb` box-shadow ring) apply unconditionally; there is no dark-mode override in the `@media (prefers-color-scheme: dark)` block (`:12-23`) that removes or reduces either, even though the file explicitly supports dark mode.
- **Rule 27 (don't mix depth techniques)** — the two floating/overlay surfaces in the file use different depth techniques: `.dialog` (`:547-554`) is border-only (`border: 1px solid var(--border)`, no shadow), while `.extpicker-menu` (`:247-260`), also a floating popover, adds a `box-shadow` on top of its border. Pick one technique for floating surfaces.
- **Rule 4 (everything deliberate)** — spacing, radius, shadow and typography have no shared scale/token to point to when justifying a value (contrast with the color palette, which is fully tokenized in `:root`). This is the root cause behind the Rule 11 (spacing), Rule 6 (no type scale), and Rule 1 (stray `#fff`/`rgba(0,0,0,…)` literals bypassing the palette, e.g. `:95`, `:526`, `:639`, `:651`) violations above — each was chosen per-selector rather than derived from a documented decision.

### Pass

- Rule 3 (high contrast for important elements) — `button.primary` (`:93-99`) uses `--accent` on white text against subtle bordered chrome elsewhere; consistent with the rule.
- Rule 7 (border contrast) — `--border` (`#d8dee4` light / `#30363d` dark) is visibly distinct from both `--bg` and `--card` in both themes.
- Rule 9 (distinct brightness values) — `--bg`/`--card`/`--border` step down in lightness consistently in both themes (aside from the Rule 15 light-mode inversion above, which is a direction problem, not a distinctness problem).
- Rule 10 (warm OR cool, not both) — all neutrals (`--fg`, `--muted`, `--card`, `--border`, `--accent`) share a consistent cool/blue tint in both themes; `--danger` is a deliberate semantic red, not a neutral, so it's exempt.
- Rule 17 (simple on complex) — `.viewer-close`/`.viewer-nav` (`:646-671`) are flat, simple circular buttons placed over photo/video content; correct pairing.
- Rule 18 (container brightness limits) — `--bg`→`--card` deltas are ~4% (light) and ~3.5% (dark), both within the 7%/12% budgets.
- Rule 19 (outer padding ≥ inner padding) — `.dialog` (`:551`, 1.1-1.2rem) vs. `.dialog-actions` gap (`:558`, 0.6rem) and `.filterbar` (`:129`, 0.5rem/1rem) vs. its child gaps (0.4-0.6rem) both satisfy the bound.
- Rule 23 (two typefaces max) — `body` (`:36-37`, system sans stack) plus `.editor-area` (`:602`, monospace stack) — exactly two typefaces, appropriately scoped to code editing.
- Rule 24 (nest corners) — `.tile` (`:453-459`, radius 10px) uses `overflow: hidden` to clip its children to the rounded corner rather than giving children a matching inner radius — this sidesteps the nesting-math problem correctly. No corner-flush mismatches found elsewhere (`.dialog`/`.extpicker-menu` children sit well inside their padding, not flush to the radius).
- Rule 25 (avoid adjacent hard divides) — `.topbar` (`:53-64`) and `.filterbar` (`:121-132`) each contribute exactly one `border-bottom`; no back-to-back divider lines found.
- Rule 28 (lower icon contrast paired with text) — `.ext-glyph` (`:283-286`) and `.group-toggle` (`:313-320`) both use `var(--muted)` next to `var(--fg)`/`var(--accent)` text, correctly softening the icon relative to adjacent text.

### Not applicable

- Rule 5 (optical alignment) — no static CSS evidence either way; would need visual inspection of the emoji glyphs used as icons (e.g. `grid.tsx:173-188`).
- Rule 8 / Rule 12 / Rule 14 (alignment relationships, visual-weight ordering, contrast-point spacing) — require rendered-page judgment, not derivable from the stylesheet alone.
- Rule 13 (12-column grid) — `.grid` (`web/src/index.css:445-452`) uses `grid-template-columns: repeat(auto-fill, minmax(140px, 1fr))`, the correct responsive pattern for a tile gallery, not a form/page layout that would benefit from a 12-col system.
- Rule 21 (line length ~70 chars) — mostly short UI copy; the one long-form spot, `.dialog` message text bounded by `max-width: min(92vw, 40rem)` (`:552`), is borderline (~90-100 chars/line at 16px) but depends on message content — not a clean-cut violation either way.

### Notes

- The color palette is well-centralized (one `:root` block, consumed via `var()` almost everywhere), but spacing/radius/shadow/typography are not — every value is a per-selector literal. Fixing Rule 11 (spacing scale) means touching most of the ~50 rules in the file individually rather than editing one token.
- Several `#fff`/`rgba(0,0,0,…)` literals bypass the token file even where the palette already has a color for the purpose (see Rule 1) — worth grep-cleaning for `#fff` and `rgba(0, 0, 0` across `index.css` when this gets fixed, not just the cited lines.
